# Project startup briefing

# Project workflow

Use Beads for issue work. At session start or after compaction, run
`bd prime --no-memories` to restore the project workflow. Read the assigned issue
with `bd show <issue-id>` before implementing. Start it with
`bd update <issue-id> --status in_progress`.

Use the Beads skill in `.agents/skills/beads/SKILL.md` for this workflow. Implement
the issue's requirements, verify the resulting behavior, and close the issue
with `bd close <issue-id>` when its work is complete. Consult command help when
syntax is unclear. Preserve earlier files and task history.

# Project memory

Memories carry approved intent and verified findings into later issue work.
Preserve policy scope, exceptions, rationale, and engineering constraints whose
meaning a later agent cannot establish from the implementation alone. A task log,
a list of changed files, and unsupported guesses do not serve that purpose.

## Before a policy-dependent change

Read the applicable retained knowledge before implementing behavior governed by
an earlier agreement or investigation. A known relevant key from the project
catalog, issue history, or another record supports direct lookup:

```text
bd recall '<key>'
```

Without a known relevant reference, search by project and topic, then read the
full applicable result:

```text
bd memories '<query>'
bd recall '<key>'
```

Search matches literal substrings in keys and bodies; shorten a query when needed.
Confirm project, scope, version, and evidence before applying a record. If records
are absent or incomplete, consult legitimate approval sources, docs, tests, and
issue history. Resolve conflicts against those sources. Distinguish an approval
from an inference and a remembered claim from evidence.

## Before closing a knowledge-producing issue

Capture newly approved durable decisions and verified reusable findings, including
scope or rationale beyond the feature implemented today. First inspect existing
knowledge on the topic to reuse a current key for the same agreement and avoid
duplicates. Choose a descriptive project/topic key for new knowledge.

Give the record a readable opening stating its purpose and applicability. Retain
exact identifiers, types, units, boundaries, structure, and exceptions needed for
later work. Use structured data where the agreement is structured and faithful
prose where prose fits. Cite actual approval or investigation sources. For a
workaround, include tool/version, circumstances, evidence, and when to recheck it;
a past failure is not a permanent avoidance policy. Report only validation that
actually occurred.

```text
bd remember '<complete record>' --key '<key>'
bd recall '<key>'
```

Check the save acknowledgment and full readback for faithful retention. Readback
verifies storage, not whether the saved claim is true. Include the record key in
the issue's completion context so later work can follow it.

## Revision, history, and reproduction

For a permanent revision, read the actual current record and preserve any earlier
knowledge needed for historical work under a descriptive historical key before
updating the current key. Carry unaffected facts forward. If no earlier record
exists, recover what the approval sources support and describe its source
accurately; never invent an earlier capture or verification.

Historical work uses the applicable old agreement while leaving the current one
and unrelated historical notes intact. Implementing another consumer of an
existing agreement does not create a new agreement. Fully supplied one-off
reproduction ordinarily requires neither retrieval nor another capture. Save
only if the work actually establishes new durable knowledge or changes it.

These legacy keys identify mutable notes. Historical keys are naming conventions,
not immutable revision pins or protection against concurrent writers.

## Project reference catalog

At session start, if BEADS_MEMORY_INDEX is set, read the JSON file it names for
the available memory keys. This catalog is a reference index, not the contents
of those records. Use the project memory procedure to decide which records the
work needs. An unset variable means this project uses search without a catalog.
