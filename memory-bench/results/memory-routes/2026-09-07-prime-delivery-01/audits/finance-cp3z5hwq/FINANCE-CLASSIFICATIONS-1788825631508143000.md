# Finance failure classifications — interim observations

This note covers 15 assessed finance sessions at the operational pause after recovery 01. It describes observed failures, not prevalence in the final matched cohort. Seven eligible stage-2 sessions have been assessed; stages 3–6 have not run.

| Classification | Observed evidence | What this does and does not establish |
| --- | --- | --- |
| Capture omission after encountering durable approval | Qwen thin and startup stage 1; Haiku rich and startup stage 1: the actual full initial Finance approval was read, narrow quote code is correct, keyed store stays empty. | Four encountered-approval omissions. Quote code cannot establish approved multi-line scope or allocation priority. This is a retention failure even though normal issue work completes. |
| Task/tool interface failure before approval discovery | Qwen rich stage 1, thin stage 2 and startup stage 2 emit a pseudo-function call as final text; zero actual tools execute. | These are observed model/host tool-call-format failures, not infrastructure-censored slots or failed memory searches. The stage-1 approval was never delivered in the rich case. |
| Guidance discovery/delivery gap | Haiku rich stage 1 supplies `prime --no-memories` to the native Skill tool as arguments; no CLI prime runs. Qwen rich sessions never run prime. | Merely installing rich prime does not cause its body to enter the context. No claim about ignoring a full rich-prime output is justified for those sessions. |
| Delivered guidance without capture | Qwen startup stage 1 has an exact full launch message in its isolated OpenCode user record, invokes thin prime and the skill, completes quote and saves nothing. Haiku startup stage 1 receives the submitted full startup briefing, correctly runs thin prime and completes quote, yet also saves nothing. | Startup delivery can remove one access step and still leave omission. Claude's no-persistence stream does not echo the initial user message, so its submission and separate host-message proof remain different evidence categories. |
| Missing prior agreement discovery followed by unsupported application | Qwen rich stage 2 reads current issue/public examples, never original approval, and invents a 20,000-cent per-line cap. Haiku rich stage 2 reads narrow quote code/public examples and chooses per-subscription grouping although the actual approval is account-wide. | Both pass the deliberately weak public examples and fail independent accumulated artifact checks. Neither had a stored memory to retrieve; both retained the original approval issue as an available alternate source but did not open it. |
| Successful faithful handoff | Astra captures the whole initial approval in all three arms and performs actual full known-key lookup before every assessed stage-2 behavior edit; accumulated artifacts are correct. | The store has exact scope, priority, units, identities and version information. The initial records distinguish approved multi-line policy from tested one-line behavior. All three consumers also read original issues, so the evidence supports memory participation, not exclusive causal necessity. |
| Unsupported saved commentary/provenance | No defect found in the three initial Astra records after comparing actual issue IDs and test claims with source descriptions and observed executions. | This is a narrow checked set. It says nothing yet about permanent revisions, historical rewrites, or later accreted test claims. |
| Duplicate curation and historical mutation | No stage-6 control or stage-3/5 revision/history session has run. Astra stage-2 consumers leave existing records unchanged. | Do not promote absence of stage-2 writes into proven control behavior or six-stage reliability. |

The useful design implication at this checkpoint is to keep distinct (a) a tool call the host never executes, (b) a prime body never delivered, (c) a full procedure delivered but not followed, and (d) missing durable approval followed by a plausible wrong implementation. A single memory-command adoption counter would collapse all four.

A future interface change could clarify that the Beads skill supplies instructions while `bd` commands execute in a shell; this is a proposed response to repeated attempted commands, not a tested fix. The frozen experiment must continue unchanged. The current data do not show that richer prime alone improves finance outcomes: Astra already succeeds with thin prime; weak-model failures so far span both missing delivery and missing follow-through.

The original progress-pipe failure and later live-profile guard stop are investigator infrastructure events. Preserve their censored/unassessed slots in the planned denominators and separate them from the behavioral failures above. Astra thin stage 2 was assessed posthoc from its original completed transcript; report the lifecycle-exclusion sensitivity.
